# HKS and Scenario Responsibility Matrix

## Meaning, evidence, and authority boundary

`HKS` is preserved as the user's literal label. This document does not invent an expansion or redefine it. An HKS scenario is used only as a cross-layer acceptance case: it must show which layer owns each truth, where the current architecture can lose it, which state is safe when that truth is missing, and which external observation proves the scenario resolved.

Evidence labels remain strict: **[CUSTOMER]** is the user's demanded experience or supplied real-world scenario, **[SCREENSHOT]** is only what the supplied UI image visibly displayed, **[MODELLED]** is a design probe, **[ATLAS]** is intended architecture, **[CODE]** is implementation inspected at `harsh/mvp@b739bd5ca682d09550acc400ed2892c38c8518f8`, and **[TEST]** is a named deterministic check. A screenshot can prove a bad card appeared, but not its code cause or a real-world outcome. The uploaded five-applications HTML is [MODELLED] reference evidence, never runtime instruction or live proof. Present, Wired, Live, Tested, and Outcome-proven are not synonyms. The matrix defines required responsibility and acceptance; it does not claim the current runtime passes the scenarios.

The governing rule is conjunctive: a downstream layer cannot repair, average over, or narrate away an upstream hard failure. If business subject, roles, permission, current open loop, accepted expertise, authority, completion, or outcome cannot be established, the item cannot be Actionable. It becomes Review source, Observation only, Defer, Suppress, Blocked, or No action/stop with an auditable reason.

## Scenario acceptance rule

An HKS replay passes only when all seven layers emit their declared receipt, the expected fail-closed state appears for every injected missing/conflicting input, and the final **Expected outcome** is externally observable or explicitly unresolved. A pass requires zero wrong-target or connector actions, zero prescriptions on uncovered, draft/unreviewed or unaccepted expertise, zero completed/superseded loops resurfaced, zero purpose/visibility escape, and zero claim/delivery event mislabelled as business success.

For every scenario, Layer 3 must expose a named-reviewer/accepted exact-hash capability closure and a per-brain Expert/Organization/Behavior/Adaptive state of selected, excluded or absent. Every selected brain must name its permitted typed consumer, exact decision field and `semantic influence`; a pinned one-brain mutation must change that intended field while all other inputs stay fixed. A hash-only delta is provenance, not authority. When a short-horizon Adaptive entry would affect the decision, the required HKS disposition is `adaptive_ttl_unresolved`: exclude it and block the dependent action rather than pretending expiry works. The current code does not enforce this disposition when expiry is omitted, so the scenario remains a failing acceptance case until the lifecycle and publication gate are repaired.

For actionable cases, the replay must expose Business subject, typed actors, exact `what remains`, why now/stakes, Evidence class and receipts, reviewed and accepted expertise, per-brain semantic influence, primary decision, materially distinct Alternative or justified sole safe action, wait/stop trigger, owner/approval, Completion, outcome window, confidence vector, end-to-end versions, and Layer 7 proposal/policy/reviewer/publisher/supersession/rollback validity. If any mandatory field fails, the correct result is the named non-action class—not a lower confidence imperative.
