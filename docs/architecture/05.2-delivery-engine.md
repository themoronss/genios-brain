# Layer 5.2 — Delivery Engine

**One responsibility:** deliver the right intelligence to the right destination, at the
right time, in the right format, with the right priority. It **distributes**
intelligence; it **never creates** it.

**Current code:** `genios_engine/deliver/` — router, channels, card_builder, digest,
outbox, push, render, agent_api, actions, bands, slots, pipeline, store. The
who/where split HAS happened: assignment and communication live in
`genios_engine/executive/` (`assignment.py`, `communication.py`), and `deliver/`
executes the plan executive authors — see `../LAYER_MAP.md` and
`genios_engine/LAYERS.py`.

## Why Delivery is its own layer

Executive Engine decides **how to operationalize** a decision. Delivery decides **who
gets it, where, when, and in what form** — a different responsibility:

> Should the extension pop up now, or wait until the user is idle? Slack instead?
> Should an agent execute it directly? A dashboard card? Suppress it because the user
> is already handling it? — that's **delivery orchestration**, not execution planning.

Isolating it means new channels (WhatsApp, Teams, voice, IDEs, autonomous agent
runtimes) can be added without touching the Executive or Reasoning engines.

## Units

```text
Delivery Engine
├── Delivery Orchestrator Unit          coordinate the delivery workflow
├── Audience Resolution Unit            WHO receives it (identity/role/ownership/permission)
├── Destination Routing Unit            WHERE it goes (+ fallback/priority routing)
├── Channel Strategy Unit               HOW it's delivered (popup/silent/card/email/Slack/agent task)
├── Timing & Interruptibility Unit ⭐    should I interrupt the user right now?
├── Delivery Policy Unit                is delivery allowed? (prefs/policy/quiet hours/rate limits)
├── Notification Unit                   human-facing (popup/toast/push/desktop/mobile)
├── Agent Delivery Unit ⭐              convert execution into machine actions for agents
├── API Delivery Unit                   expose externally (REST/GraphQL/Webhook/MCP/SDK/stream)
├── UI Delivery Unit                    cards/widgets/badges across every surface
├── Delivery Tracking Unit              queued/delivered/viewed/dismissed/accepted/executed/failed/expired
├── Delivery Retry Unit                 retry/fallback/escalate/alternative-channel/cancel
├── Delivery Analytics Unit             open/execution/dismiss rate, latency, notification fatigue
└── Delivery Object Builder             the standardized output object
```

### Timing & Interruptibility Unit ⭐⭐⭐ (very important)
"Should I interrupt the user?" — **DO** interrupt for churn risk / security issue /
overdue investor follow-up; **DO NOT** interrupt for weekly summaries / low-priority
optimization / marketing suggestions. Signals: calendar, active meeting, focus mode,
current task, notification history, urgency, business impact.

### Agent Delivery Unit ⭐ (machine consumers)
Agents read **structured intelligence, not language** — Decision/Priority/Evidence/
Constraints/Recommendation as JSON. Converts the Execution Object into agent
instructions (Email/Calendar/CRM/Coding/Admin/Sales agents) and monitors them.

## Destinations

Browser extension · desktop app · mobile app · dashboard · Slack · Teams · email ·
calendar · API · webhook · MCP · SDK · CRM · ERP · IDEs (Cursor / Claude Code / VS Code) ·
internal agent runtimes. **Same object, different adapters.**

## The Delivery Object (contract)

```json
{ "recipient": "Rohit", "channel": "Browser Extension", "priority": "High",
  "interrupt": true, "delivery_time": "now", "payload": { }, "tracking": true }
```

## LLM usage in Layer 5.2

Only for copy — rewriting notification text, drafting emails, generating Slack
messages, adapting tone, summarizing long plans. **Never** for routing, timing,
audience selection, interruption decisions, or policy validation (all deterministic).

## Storage

Supabase: delivery queue/history, notification history, tracking, preferences,
execution status. Redis: active queues, real-time delivery, session context, rate
limiting. **No permanent business knowledge stored here.**

## Frozen decisions

- Delivery distributes; it never creates intelligence.
- The workflow-bridge only **hands off** to external tools — it does not automate them.
- Interruptibility and policy are deterministic; only copy uses an LLM.
- Clean boundary: **L5 = how to execute · L5.2 = who/where/when/what-form · L6 = what we learned.**
