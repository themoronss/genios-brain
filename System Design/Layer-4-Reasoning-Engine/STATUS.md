## The standard a finished folder meets

Use a completed folder — `01-Situation-Understanding/core.dependency/` is a good one — as the
reference. Every file carries four movements: **what it is for → what exists → how it works →
examples and edge cases**, with:

- every number read out of the source or produced by executing it, never remembered,
- worked examples with real values, not "the score is computed",
- explicit silence semantics — what the module does when it has nothing to say,
- Mermaid diagrams with prose beside them carrying the *why*,
- bugs and compromises documented rather than papered over.

## Findings the completed folders surfaced

Documenting the code found real issues. These are recorded in the relevant unit folders and are
worth reading before changing anything nearby:

1. **`core.dependency`'s `prerequisite_absent` plugin is unreachable in the orchestrated path.** Its
   default prerequisite source is `capability.required_fields`, and the orchestrator sets a terminal
   `INSUFFICIENT_CONTEXT` before the plan loop when any of those is absent — so the unit is skipped
   before the plugin can speak. Verified end to end.
2. **Config validation is eager in one place and lazy in five** across `core.dependency`, so an
   out-of-range value in five of its six keys only raises on the branch that reads it.
3. **`core.dependency` reads past its own `UnitView`** — it declares no `required_fields`, so
   `view.facts` is empty and its plugins read `request.context.facts` directly. Declaring the fields
   would make the orchestrator refuse the run on exactly the deals the unit exists for.
4. **`unblocked_bp` is applied capability-wide** by its only consumer, so a blocker on one play caps
   readiness for plays that blocker has nothing to do with. No blocker-to-play mapping exists
   anywhere in Layer 4.
