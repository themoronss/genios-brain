# Layer 7 Learning — Current Successes, Failures, and Expected Behavior

## Blunt verdict

Layer 7 has real infrastructure and several defensible deterministic safeguards, but it is not yet the closed learning loop promised by Atlas. The strongest Verified success is that completed execution, receipt-backed delivery, outcome analysis, validation, immutable proposal storage, versioned publishing, and rollback have concrete code paths. The decisive Current failure is reconciliation: explicit card corrections, structured execution outcomes, delivery facts, and user-facing value analytics do not become one canonical causal record. Three direct learning units and both direct personalization-evolution units currently emit no proposal.

The correct customer-facing statement is therefore: **GeniOS can calculate and govern some learning candidates; it cannot yet prove that customer correction and business outcomes reliably change future intelligence.**

## Evidence standard

Every row below is pinned to `harsh/mvp@b739bd5`. “Verified success” means code or migration evidence survives to the stated boundary; it does not mean the behavior is Live for a tenant or Outcome-proven. Atlas expectations are design requirements, not implementation evidence.

## What should have happened in the reported intelligence failure

For the Theresa/Antler scenario, Layer 7 should not learn “rejected investor” from silence. Layer 1 must preserve Theresa’s statement that future updates could trigger reconsideration; Layer 2 must reduce the thread into `reconsideration_possible`, update cadence, last meaningful update, unanswered count, and owner; Layer 3 must supply fundraising follow-up expertise; Layer 4 must recommend the next justified update or defer; Layers 5–6 must create and deliver an accountable action; only then may Layer 7 observe delivery, reply/reconsideration, attention cost, and outcome. Silence with unknown exposure remains unknown. A later reply can update the bounded play; a click or generic card cannot.

## Success inventory versus customer value

The existing strengths are worth retaining: deterministic validation, neutral outcome handling, receipt-backed delivery facts, immutable proposals, target-restricted publishing, Expert review-only behavior, versioning, idempotency, and rollback. They lower the chance of unsafe self-modification.

They do not by themselves meet the customer promise. The missing proof is one replayable chain from human correction or external result to a scoped brain version, to a changed Layer 3 compilation, to a better future decision, to a measured outcome versus counterfactual. Until that chain is green, Layer 7 remains **framework-ready, not live-ready**.

## Reset storage truth

| State class | Storage and reader Evidence | What reset actually does | Current failure if misunderstood | Should have happened |
|---|---|---|---|---|
| Runtime temporary memory/lease | `feedback/publisher.py:106-115` inserts `temporary_memories` with mandatory `expires_at`; `feedback/consumer.py:90-99` reads only active rows whose expiry is after `now` | `feedback/reset.py:33-36` deactivates every matching pre-reset `temporary_memories` row and truncates expiry to the reset clock | Names such as `adaptive_expired` make Runtime leases look like Adaptive Brain rows | Report `runtime_memories_expired`; prove no Runtime value is consumed after reset |
| Organization learned entry | `learned_brain_entries`, selected by active version without an expiry predicate (`feedback/consumer.py:78-88`) | No update; entry remains active | Stale ICP/policy may survive the pivot | Revalidate under current Organization authority and publish a governed superseding/disabled version; invalidate dependent snapshots |
| Behavior learned entry | `learned_brain_entries`, selected by active version without an expiry predicate | No update; entry remains active | Old behavior may be wrongly treated as current or company-wide | Re-evaluate scope/support/freshness and separately supersede or retain with an explicit no-effect receipt |
| Durable Adaptive learned entry | `learned_brain_entries`, selected by active version without an expiry predicate | No update; entry may remain active indefinitely | A pivot appears safe because Runtime rows expired while durable Adaptive still influences permitted consumers | Block non-expiring Adaptive publication; for an existing row, separately deactivate/supersede under governed policy and prove zero later selection plus safe rollback |

The distinction is mechanical: the reset query never references `learned_brain_entries`. A situation rerun after reset does not itself revoke a durable brain version. Until a separate governed operation changes those active rows and invalidates dependent snapshots, the honest state is **Runtime reset complete, durable-brain reset incomplete**.
